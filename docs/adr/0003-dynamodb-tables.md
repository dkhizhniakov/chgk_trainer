# ADR-0003: Три таблицы DynamoDB по доменам

**Статус**: принято

## Контекст

Классический подход DynamoDB — single-table design. Но домены приложения слабо пересекаются в запросах: контент (общий, редко меняется), база знаний (общий, граф связей), пользовательские данные (приватные, частые записи).

## Решение

Три таблицы: `content`, `knowledge`, `userdata`. Внутри каждой — single-table паттерны: обобщённые `PK/SK`, перегруженные `GSI1`, `GSI2`.

## Последствия

- (+) Проще рассуждать о ключах и IAM: например, отдельные политики, разные настройки бэкапа/TTL/streams.
- (+) Удаление пользователя или перенос контента — по таблице, без риска задеть другие данные.
- (−) Запрос «вопрос + связанные сущности» — два обращения к разным таблицам (выполняются параллельно).
- (−) Транзакции между таблицами возможны, но связь вопрос ↔ сущность хранится целиком в `knowledge`, чтобы их избегать.
